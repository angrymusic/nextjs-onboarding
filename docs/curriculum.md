## 과제 2. 서버/클라이언트 컴포넌트 경계 ★ 최중요

**목표**: "어디까지 서버, 어디부터 `'use client'`" 감각 형성

**과제**
- 서버 컴포넌트에서 데이터 읽어 렌더 (fetch 또는 mock)
- 인터랙션 부분(버튼, 토글)만 `'use client'`로 분리
- 의도적 실수 체험:
  - 서버 컴포넌트에 `useState` 넣고 에러 메시지 읽기
  - 클라이언트 컴포넌트의 `children`으로 서버 컴포넌트 전달하는 패턴 구현

**완료 조건**: 각 컴포넌트가 왜 server/client인지 한 줄씩 주석으로 설명

**던질 질문**
1. `'use client'`를 붙이면 그 파일만 클라이언트가 되는가? (아니오 — import 트리 전체. 경계 개념 확인)
2. 서버 컴포넌트 코드는 브라우저 번들에 포함되는가?
3. 클라이언트 컴포넌트 안에 서버 컴포넌트를 넣고 싶으면 어떻게 하는가? (children/props로 내려주기)
4. Vue에는 이 구분이 없었는데, 이 구분으로 얻는 것은 무엇인가? (번들 크기, 데이터 접근, 시크릿 보호)
5. 서버 컴포넌트에서 `onClick`을 달면 무슨 일이 일어나는가?

## 과제 3. 모달 = Parallel + Intercepting Route ★ 고난도, 1~2일

**목표**: 실제 프로젝트의 모달 패턴 그대로 이해

**과제 (3단계로 분할)**
- (a) Parallel route만: `@modal` 슬롯 + `default.tsx`. `default.tsx`를 일부러 빼고 404 직접 경험
- (b) Intercepting 추가: 목록 → `(.)items/[id]` 클릭 시 모달, 새로고침 시 풀페이지
- (c) 마무리: 모달 닫기 `router.back()`, URL 직접 진입 시 풀페이지 확인
- (d) 실제 프로젝트의 모달 코드 읽고 파일 구조/렌더 흐름 그림으로 그려오기

**Vue 매핑**: parallel route ≈ named `<router-view>`. intercepting은 Vue에 대응 개념 없음 — "소프트 내비게이션일 때만 가로챈다"

**함정 미리 공유**
- `(.)` 매칭은 파일 경로가 아니라 **세그먼트** 기준 (route group `(group)`은 무시됨)
- 다른 페이지로 이동해도 모달이 남는 문제 → `default.tsx` 또는 catch-all로 처리

**완료 조건**: 클릭 진입 시 모달 + 뒤에 목록 유지, 새로고침/직접 진입 시 풀페이지

**던질 질문**
1. 목록에서 클릭했을 때와 URL 직접 진입했을 때, 각각 어떤 파일이 렌더되는가? (핵심 질문)
2. `default.tsx`는 언제 렌더되는가? 없으면 왜 404가 나는가?
3. `(.)` `(..)` `(...)`의 차이는?
4. 모달을 닫을 때 `router.back()`과 `router.push('/list')`의 차이는? 어느 쪽이 왜 맞는가?
5. 이 패턴 대신 그냥 zustand로 모달 open 상태 들고 있으면 안 되나? 이 패턴의 장점은? (URL 공유 가능, 새로고침 대응, 브라우저 히스토리)
6. (d)에서 그린 그림 보면서: 우리 프로젝트에서 이 모달이 풀페이지로 열리는 경로는 어디인가?

## 과제 4. TanStack Query CRUD

**목표**: 서버 상태 관리 멘탈모델 전환

**과제**
- 목록 조회 `useQuery` (queryKey 설계 포함)
- 생성/수정 `useMutation` + `invalidateQueries`
- 로딩/에러 상태 UI 처리

**Vue 매핑 (최대 습관 차이)**: Pinia처럼 서버 데이터를 store에 복사하지 않는다. 서버 상태는 query가 소유하고 캐시가 곧 저장소

**완료 조건**: 뮤테이션 후 목록 자동 갱신, store에 서버 데이터 복사 없음

**던질 질문**
1. queryKey는 왜 배열인가? 어떤 기준으로 설계했는가?
2. 뮤테이션 후 목록이 갱신되는 원리는? invalidate는 정확히 무엇을 하는가?
3. `staleTime`과 `gcTime`의 차이는? staleTime 동안 refetch가 일어나는가?
4. Pinia로 하던 방식과 뭐가 다른가? 서버 응답을 zustand에 넣으면 왜 안 되는가?
5. 같은 useQuery를 두 컴포넌트에서 호출하면 요청이 두 번 나가는가?

## 과제 9. Middleware

**목표**: 요청 파이프라인 이해

**과제**
- `middleware.ts` 작성: 인증 쿠키 없으면 `/login` 리다이렉트
- `matcher`로 대상 경로 제한, 정적 자산 제외

**Spring 매핑**: Filter/Interceptor와 같은 자리. 차이점 강조:
- Edge 런타임 — Node API 대부분 사용 불가
- 앱당 1개, 체이닝 없음
- 매칭되는 모든 요청에 실행 — 무거운 로직 금지 (DB 조회 등)

**완료 조건**: 미인증 리다이렉트 동작, matcher에서 `_next/static` 등 제외

**던질 질문**
1. middleware는 어디서 실행되는가? 서버 컴포넌트보다 먼저인가 나중인가?
2. Spring Interceptor랑 뭐가 같고 뭐가 다른가?
3. middleware에서 DB를 조회하면 왜 안 되는가?
4. matcher를 안 쓰면 어떤 요청까지 middleware를 타는가?
5. 실제 프로젝트 middleware는 무슨 일을 하고 있는가? (코드 읽고 설명시키기)
